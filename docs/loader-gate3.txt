Four verdicts, each a different check:

- IDENTIFY: the arch route finds `gemma_vq` and the family gate accepts
  `gemma_vq.format_version` 1 (identify.rs, the gate beside GLM's).
- META: 16 integer hparams, 3 floats, the `attention.causal` flag, and the two
  per-layer arrays — their lengths, the KV head counts (2 sliding, 1 on layers
  5/11/17/23) and the sliding-window pattern's 20/4 split on exactly those four
  layers — were all read back and matched `SHAPE_GEMMA_VQ`.
- BIND: the 1376 names the family's bind list declares are all present.
- LAYOUT: the family table's 1376 (name, type, rank, dims) tuples equal the
  file's, which for the 461 VQ tensors means the table's byte length — computed
  from the tower architecture by the reference's own account — equals the payload
  length the writer wrote. The table was written by hand from the checkpoint's
  architecture and matched on the first run; that is the check working, not a
  coincidence of the gate being weak: `validate_layouts` compares ndim and every
  dim exactly for this class.

The harness copies the artifact once, and for each case reflinks a fresh copy,
patches one field and requires (a) a non-zero exit and (b) the named refusal. The
last thing it does is load the untouched copy again and compare the dump, so it
cannot pass by failing everything. The patch offsets are the manifest's own
absolute offsets and the first padding byte the manifest implies; no offset is
hardcoded except the payload header's 16 bytes and its 32768-byte codebook, both
of which section 2 of the contract measured.

3. What the validator checks, and the one check this tier cannot make

Per VQ tensor (`gemma_vq.rs::payload`), in order:

- rank 1, and the payload's first four bytes are `DQVQ` (ds41_vq_fmt.h:32);
- `dim` and `nc` nonzero, `cols % dim` zero, rows and cols nonzero;
- the reference's byte account `vq_payload_bytes(rows, cols, dim, nc)` equals the
  length the FILE declares for this tensor — the same expression the writer and
  the size allocator share (vq_qc_bytes.h:15, :20);
- every codebook word finite (16384 words per payload);
- every row gain finite and nonzero (the contract's section 6 wording).

Then the file-wide rules the two shipping families share: unique names, ranks
1..4, no zero dimension, 32-byte alignment, zero padding up to the data position
and between tensors, the first tensor exactly at `DATA_POS`, the last ending
exactly at the file's end, and no split.

The index-stream bound is settled by the account rather than by a scan, and here
is the arithmetic rather than an assertion. At this tier `nc` is 4096, so the
index width is 12 bits (`vq_qc_bytes.h:15`, and the decoder's identical loop at
ds41_vq_fmt.h:87), the mask is 0xFFF and every 12-bit value lies in `0..4096`.
**An out-of-range index is not representable at nc = 4096**: the index space and
the codebook are the same size. The reachable tamper is a header whose geometry
no longer reproduces the declared length, which is exactly what the account
refuses — cases 2 and 3 of the gate. A future tier whose codebook is not a power
of two would have slack above `nc - 1` and would need the scan; that is recorded
as an open item rather than implemented against a case that cannot occur.

The C identity is the family enum value 16, the variant 19, `DS4_SHAPE_GEMMA_VQ`,
the shape switch arm and the `weights_bind` arm. The shape now exists in three
places — ds4.c, `crates/ds4-core/src/shape.rs` and `tests/parity/shape_c_oracle.c`
— and `dump_oracle` prints the Rust copy while the oracle prints its own, so the
parity test compares them field by field. That test passed on the first run of
the three-way copy, which is the only mechanical guard against a hand-copied shape
drifting.

The bind is a stop, not a stub, and the reason is in the file: `weights_bind`
falls through to the DeepSeek binding when a family has no arm, so a `gemma_vq`
artifact would otherwise be bound as another architecture and load a shape of
garbage instead of failing. The weight struct and the graph arrive with phase 4
(`ds4_eg2vq_graph.inc`); until then the arm refuses by name.

Two pre-existing environment facts, both measured here, neither caused by this
change and both material to phases 4 and 7:

- `make ds4-c ds4-server` cannot relink in this working copy. `ds4_cuda.o`
  (2026-10-14 20:15) is older than the CUDA sources it depends on
  (`cuda/glm_vq.cuh`, `cuda/l31_flash.cuh`, `ds4_glmvq.h`, all 2026-10-18), so
  make rebuilds it, and that rebuild fails in ptxas with
  `Feature 'mbarrier.try_wait.parity' requires .target sm_90 or higher` and
  `cp.async.bulk.prefetch` errors — the tree's `.ds4-cuda-config.mk` pins
  `CUDA_ARCH := native` (sm_89 on this machine). `ds4.o` and `ds4_cpu.o` build
  fine; the CUDA object is a separate, larger question about the copied tree.
- `/data/build/linux/build.sh -p /data/embeddinggemma2/ds4-rs` refuses this
  project's binaries: `error: target ds4-agent-rs in package ds4-cli requires the
  features: native`. The canonical builder has no way to pass `--features native`,
  which every `ds4-cli` binary needs, so this tree's Rust deliverables are built
  by the Makefile plus `cargo` with that feature (rule 5's documented
  iterative-development exception). Both facts belong in the handoff.

6. What this proves, and what it does not

Proves: the ds4 host identifies the artifact as its own family, validates every
one of its 1376 tensors and each of the 461 payloads against the payload's own
header and the reference's byte account, agrees tensor for tensor with the
writer's manifest, loads identically twice, and refuses eight named tamper cases
including a bad metadata value and a bad payload byte. The C side's copy of the
shape is compared against the Rust copy by the existing parity test.

Does not prove: that a single number the model computes is right. There is no
graph, no tokenizer and no forward pass yet — the tokenizer refuses by name and
the bind stops by name, both deliberately, both phase 4. The layout proves the
shapes, not the arithmetic. And the C `DS4_SHAPE_GEMMA_VQ` is verified only as a
table: nothing consumes it until phase 4 builds the graph.
