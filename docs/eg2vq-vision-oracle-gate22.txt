The vision oracle — phase 8, unit 22 evidence (2026-10-19)

What this records, and why the instrument had to be built

Phase 8 ports EmbeddingGemma-2's VISION tower: image -> vision tower -> 3x3
average pool -> sqrt(n_embd) -> weightless RMS -> the 768-to-512 tie-in
projection -> soft tokens spliced into the text tower at its image-token spans ->
the same 768-dim embedding the text path produces.  This project gates every
ported tower against a frozen reference, and for TEXT that reference was a
shipped binary (llama-embedding at the pin, docs/anchor-gate2.txt).  For images
none exists: examples/embedding/embedding.cpp has no mtmd, mmproj or image
support at all, and tools/mtmd/mtmd-cli.cpp has no embedding or pooling mode
(grepped at the pin, both empty).  The Python ML stack is gone by owner
instruction, so the pin's own converter cannot run here either.  The reference is
therefore an instrument this project builds, exactly as the baseline text GGUF
was: OUR OWN WRITER emits an mmproj, and a harness linked against the pin's own
mtmd runs one image through it and dumps what comes out.

Everything below was run in this session; every number was printed by the command
recorded beside it.

Two transforms, both the converter's own:
  - the patch embedder is a linear [768][3*16*16] in the checkpoint and a CONV in
    the mmproj, so its bytes are permuted exactly as conversion/gemma.py:1046-1050
    does it: dst[c*P*P + y*P + x] = src[(y*P + x)*3 + c], P = 16.
  - every other 2-D weight is the checkpoint's with its dims reversed (HF [out][in]
    -> GGUF ne [in, out]); the 1-D norms and the position table keep their order.

Two dtypes, and the second one is forced rather than chosen: the matmul operands
keep the checkpoint's bf16, while the six norms and the position table are widened
to f32 because the reference's OWN graph refuses the alternative — measured this
session, the first attempt aborted with
    binary_op: unsupported types: dst: f32, src0: f32, src1: bf16
(ggml-cpu/binary-ops.cpp:135, inside ggml_compute_forward_mul) from the norm
multiply, and the position table's rows are ADDED to the patch embeddings
(gemma4v.cpp:46-47).  The converter agrees on both (conversion/gemma.py:1015-1018
forces the position table to F32; gguf-py writes the 1-D norms as F32).

The preprocessing, measured rather than assumed

The reference's own preprocessor ran and reported it:
  clip_encode: copying image 1/1 to input buffer (nx=528, ny=384)
  clip_encode: output embedding shape [512, 88, 1]
which is the arithmetic read from the source beforehand — mtmd's dyn_size
preprocessor (tools/mtmd/mtmd.cpp:953-959) resizing with calc_size_preserved_ratio
(mtmd-image.cpp:122-156) at align_size patch * n_merge = 48, bicubic, between
image_min_pixels 161,280 and image_max_pixels 2,580,480 (= 70 and 1120 tokens'
worth of pixels, clip-model.h:204-211 with the limits set at clip.cpp:1734), and
the image-token count ((nx/16)*(ny/16))/9 (clip.cpp:4419-4428): 512x384 -> 528x384
-> 33x24 = 792 patches -> 88 soft tokens.  The loader's own hparams dump printed
n_merge 3, image_min_pixels 161280, image_max_pixels 2580480, matching to the
digit.  Our port's preprocessing must reproduce this exactly, and the fixture
bytes are frozen (below) so it can be checked.

The splice, and how the reference builds it

The input is mtmd's own sequence for one image: the leading text chunk (BOS + the
begin marker "<|image>" = 2 tokens), the image span (88 soft tokens), the trailing
text chunk ("<image|>" + EOS = 2 tokens) — 92 positions in all.  The reference
carries the image span as EMBEDDINGS in one batch with the text tokens, which is
the one thing about this path that is not obvious:

  - mtmd_helper_eval_chunks does NOT do it: it evaluates chunk by chunk, and for
    an embeddings model the pooling is per batch, so the pooled vector it leaves
    behind describes the last text chunk alone.  MEASURED: with the helper, two
    visibly different images produced byte-identical pooled vectors (their soft
    tokens differed, sum of squares 69219.02 vs 65827.22, while the pooled dumps
    were identical to the last byte).  The gate now proves the opposite.
  - the public llama_batch cannot carry the mixed batch either: this version's
    compat conversion (src/llama-batch.cpp:1410-1484) stores embeddings only when
    the batch has NO token array, so a batch built that way loses the image rows
    and SEGFAULTS — measured: exit 139 inside the first encode.
  - what works is the reference's own llama_batch_ext, which its image path uses
    (mtmd-helper.cpp's decode_embd_batch): token entries for the text, embedding
    entries for the image span, each with its own position, all in sequence 0, and
    one llama_process over the lot.

What the gate does and what it prints

  MMPROJ GATE: the reference accepted the mmproj (211/211 tensors agree with the writer's manifest),
  MMPROJ GATE: the writer is deterministic (sha256 9ffb86e3...), the frozen reference reproduces for both
  MMPROJ GATE: fixtures, and the two fixtures differ (cosine 0.786465)

  The tensor check is deliberately two-sided: the writer's manifest against the
  reference's OWN per-tensor readout of the file it just loaded (211 lines, name,
  rank, dims, byte count and type).  A file only this project can read would be
  worthless as a reference, so the check is the reference's acceptance, not ours.
  Log: out/eg2vq-vision-oracle-gate22.log.

What this does NOT prove

  - Nothing about the port.  No ds4-rs code computes anything here yet; unit 23
    (the CPU vision tower) and unit 24 (the device path) are what this reference
    exists to gate.  The oracle is the denominator, not the result.
  - Nothing about bf16 vs f32 in the norms as OUR port will read them: the port
    reads the artifact, where the vision tower is the checkpoint's bf16 verbatim
    (class `keep`), while this oracle's norms are f32 because the reference graph
    demands it.  That difference is real, it is one rounding of a few hundred
    values, and unit 23's gate must declare a tolerance that contains it — it has
    NOT been measured yet.
  - Nothing about other images: two fixtures is a first gate, not coverage.  A
    real photograph, a wide aspect, and an image whose patch grid does not divide
    by 3 along one axis are all still unmeasured.
  - Nothing about the audio tower, the video processor, or the 280-soft-token
    default the checkpoint's processor_config.json declares (our fixtures land on
    88 because mtmd's own limits, not the checkpoint's default, drive the grid).

Rule 19, stated rather than assumed: `bash tests/qa-gate.sh` prints
`QA GATE: overall PASS` for this unit, and the honest reason is that this unit adds
no RUNTIME surface at all — the gate's patterns track C engine entry points
(`ds4_*` definitions), HTTP endpoints and Rust `pub fn`s, and unit 22's new files
are a C writer, a C++ harness and a shell gate, none of which is an interface the
gate models. Its only reported surface is `embed_caps`, unit 20's, still covered by
qa-evidence/qa-report.md. Unit 23, which does add an engine entry point, WILL trip
the gate and must carry its own QA pass before any push offer.
