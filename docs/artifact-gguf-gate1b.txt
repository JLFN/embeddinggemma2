family — the file the ds4 port will load — and the gate that it carries exactly
what the container carries, tied to the checkpoint on one side and to the port's
own reader on the other. Everything below was run in this session; where a number
is quoted it was printed by the command shown next to it.

  Per-slot checks the writer refuses to write without, every one of them a
  comparison between two independent sources (container slot table, the payload's
  own 16-byte header, the checkpoint's safetensors shape):

  - a VQ slot: the payload's magic is `DQVQ` (ds41_vq_fmt.h:32), its dim/nc/rows/cols
    equal the slot's recorded geometry AND the checkpoint's shape, and its length
    closes the reference's own byte account `vq_payload_bytes(rows, cols, dim, nc)`
    (vq_qc_bytes.h:20) — the same formula the container's checker used
    (tools/eg2_pack.c:1044). Shipped as type 42, nd 1, ne = {payload bytes};
  - the token table: cols a whole number of q8_0 blocks and
    bytes = rows x cols/32 x 34 (ds4_quantfmt.c:17: 32 values in 34 bytes). Shipped
    as type 8, nd 2, ne = {512, 262144};
  - a verbatim slot: source dtype BF16 and bytes = the checkpoint's element count
    x 2. Shipped as type 30 at the checkpoint's own rank;
  - every slot's name exists in the checkpoint, the container's src_dtype equals
    the checkpoint's dtype, and the container's slot count equals the checkpoint's
    tensor count (1376) — a partial container cannot be wrapped into a whole-looking
    file.

  Both differences are deliberate: the contract's table (section 4) carries the
  family gate and the recipe, and the one shipping VQ-to-GGUF tool writes no
  general.file_type for a VQ family (v41_to_gguf.c:357-363). The hparams and the
  tokenizer are emitted by one shared function per block, so the two files cannot
  drift on a value; this differential is how that is checked rather than asserted.

4. Determinism

  A second run of the same command (to /tmp) produced the identical digest:
  5bcf22161dda46bccbd5123b26d519efccad981cbfe11cce7227415b3373b33f, 0.94 s wall.
  The re-wrap is a copy of a deterministic container through a writer whose
  header depends only on its inputs, so the artifact is bit-reproducible.

6. One correction to the contract, measured

  The contract said the 914 verbatim tensors ship "nd 0..4 from the checkpoint".
  They cannot: 480 of them are rank-0 scalars in the checkpoint (shape [], e.g.
  audio_tower.layers.0.feed_forward1.ffw_layer_1.input_max, 2 bytes), and BOTH
  readers of this file reject a rank-0 tensor —

    ds4.c:3353   if (t->ndim == 0 || t->ndim > DS4_MAX_DIMS) ds4_die("tensor has an
                 unsupported number of dimensions");
    crates/ds4-core/src/tensors.rs:266   if ndim == 0 || ndim > MAX_DIMS { return
                 Err(TensorError::BadDims) }
    ggml.c:1786  GGML_ASSERT(n_dims >= 1 && n_dims <= GGML_MAX_DIMS);

  — so a scalar ships as the one-element vector it is: rank 1, ne = {1}, which is
  the same shape the baseline gives its 24 layer_output_scale tensors. The file's
  rank census above (0 rank-0 tensors) is the result. Contract sections 4 and 5
  are corrected in the same commit.

7. What this file is, and what it is not

  - It is ds4's file, not llama.cpp's. Our private type numbering (42 vqblob,
    40/41/43/44 beside it) is ds4's own; llama.cpp assigns 42 to Q2_0 and refuses
    the same tensor as a bad block size, and gguf-py refuses it identically:

      E gguf_init_from_reader: tensor 'audio_tower.layers.0...linear.weight' of type
        42 (q2_0) has 1613841 elements per row, not a multiple of block size (64)
      ValueError: Quantized tensor row size (1613841) is not a multiple of Q2_0 block
        size (64)

    Both runs are expected and are the reason phase 2's anchor leg uses the
    BASELINE GGUF (bf16/f32 only, which llama.cpp loads) and the artifact's
    acceptance leg is the port's own reader. This is also why the family is
    identified in the file itself (`gemma_vq.format_version`), not by guesswork.
  - It does not prove the port's arithmetic: that is phase 4, against the frozen
    anchor. It does not prove the payloads' quality: the encoder measured each
    payload against its source matrix (docs/artifact-verify-summary.txt), and
    phase 5 measures the whole model; the token table's own number, from the
    encoder's log, is cos 1.0000 / relL2 0.5484% at q8_0
    (out/encode-log.txt, language_model.embed_tokens.weight).
  - It does not yet load: the Rust-side payload validation the contract assigns to
    the loader (magic, geometry, byte account, index-stream bound, row gains,
    codebook finiteness) is phase 3, and the runtime that reads this file does not
    exist yet.
