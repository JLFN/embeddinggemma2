Phase 7 evidence — the gemma_vq device path
===========================================

Unit 17 of embeddinggemma2-handoff.md.  Phase 7 is the phase the owner's
directive of 2026-10-19 opened ("we need to get cuda support, it should much
faster"): the text tower on the GPU, weights device-resident, the VQ payloads
consumed in-kernel.  Its rows are P3.1 (the dim-4 VQ device kernel), P3.2 (a
bidirectional attention kernel with the symmetric sliding mask) and P3.3 (the
tower end to end, with latency and VRAM printed by the run).

This document is the evidence for the slices as they land; each section names the
row it belongs to.  Sections 1 to 4 are single-kernel measurements (arithmetic and
throughput, no item-level claim); section 5 is the end-to-end tower, where the
tokens-per-second, VRAM and parity numbers live, and section 6 is what even that
does not prove.

1. Row P3.1 — the dim-4 DQVQ device GEMM
----------------------------------------

1a. What exists now

  ds4-rs/cuda/eg2vq_vq.cuh        the kernel family and its launcher
  ds4-rs/tests/test_eg2vq_vq.cu   its gate
  ds4-rs/Makefile                 tests/test_eg2vq_vq and test-eg2vq-vq

Nothing else in the tree changed: the family's CPU reference path
(ds4_eg2vq_graph.inc), its binder, the Rust host and the artifact are untouched,
so this slice cannot have moved any earlier number.

1b. Design, and what it was read from

The authority for the payload is ds41_vq_fmt.h:73-105 (`ds4vq_dequant_f32`): the
value rule is value[row][col] = codebook[idx][col % dim] * gain[row], dim is 4
for this tier (ds4_eg2vq.h:29-38), and the index stream is one continuous
little-endian bit stream whose width follows the codebook size (12 bits at
nc = 4096).  The on-device pattern comes from cuda/ds41_vq_row.cuh: the payload
open re-checks the five header fields against the caller's expectation
(:44-72), the codebook lives in shared memory, the bit stream is read as whole
words and extracted with __funnelshift, and the multiply-add expression is the
one place arithmetic identity with the reference is decided (:107-118).

Three deliberate differences from that row kernel, each of them a consequence of
this family's geometry rather than taste:

  dim 4, not 8         one 12-bit index covers four weights; a codeword is 8 B.
  a GEMM, not a dot    the tower runs whole items through a matrix (26 to 1414
                       tokens), so a block keeps a 64-token x 64-row tile and
                       reuses each decoded codeword across the tile's tokens.
                       The per-row kernel would re-read the index stream once
                       per token.
  f32 in, f32 out      the reference path is f32 and the activation is orders of
                       magnitude smaller than the weights, so the device adds no
                       rounding the reference does not have.  (The tree's own
                       prefill kernels take f16 activations, which is right for
                       a 35B model and wrong here: the point of this family is
                       that the artifact is not less smart.)

Tile: 16 x 16 threads = 256; per block, 64 tokens (4 per thread column) x 64 rows
(4 per thread row) x a 256-column K slab; 16 f32 accumulators per thread.  Shared:
the codebook at 32 KB (4096 x 4 f16, loaded once per block) and one 8 KB index
slab (64 rows x 64 codewords, uint16).  That is 40 KB, under the 48 KB static
limit, so the kernel needs no dynamic-shared opt-in and does not trade occupancy
for it.  Each thread unpacks its own 16 codewords per slab (24 B = six words)
with __funnelshift, and reads its four tokens' four activation values as float4.

1c. The gate, and why it has two references

  make tests/test_eg2vq_vq && ./tests/test_eg2vq_vq      (exit 0 required)

  ds4-rs/tests/test_eg2vq_vq.cu builds payloads at the tower's own geometries and
  a spread of token counts, and compares the kernel against

  (a) its own decoder of the same bytes, which is checked against the values that
      were packed into them — so a packing mistake cannot hide behind the decode;
  (b) an FP64 dot over that decoded matrix, which is the arithmetic the kernel's
      f32 accumulation must land on.  Inputs are f32 and codeword and gain values
      are exact f16 -> f32, so summation order is the ONLY error the kernel can
      have; the declared bound is 1e-5 relative RMS and a per-token cosine of 1
      to 1e-6, both far above what f32 rounding of a 512 to 2048 term dot costs.

The synthetic payloads are packed by the test's own p_pack, which mirrors the
project's writer byte for byte (/data/YoungAi/gguf-tools/quantize/vq_qc.h
`vq_pack`:242-266): header, nc*dim f16 codebook, rows f16 gains, one continuous
little-endian 12-bit stream, padded to whole bytes plus one guard byte.

A payload bound to the wrong geometry must decode nothing: the test asks for 1024
rows from a 512-row payload and requires the output to be untouched.

Read the rel RMS column as "the kernel is the arithmetic it claims to be": at most
8.2e-07 of the reference, with identical rankings.  The GFLOP/s column is a single
kernel at one geometry, not the tower: at 184 tokens the tower is ~49 GFLOP, so
3.1 TFLOP/s is the order of 16 ms of GEMM per item — a shape that the CPU path
spends ~1400 ms on at -O0 (measured, phase 5).  Whether that becomes a tokens/s
number, and how much of it survives the rest of the tower, is what P3.3 measures.

The GB/s column is the payload traffic the design implies, not a bandwidth bound:
the payload is re-read once per 64-token tile, so a long item reads each matrix
ceil(tokens/64) times.  It is reported so a later slice can see whether raising
the token tile (or splitting K) is worth anything.

2. Defects this slice found, measured
----------------------------------------------------------------

2a. In the CPU path's decoder (not the kernel)

Writing the kernel surfaced a divergence that is not the kernel's:

  ds4vq_f16 (ds4-rs/ds41_vq_fmt.h:38-43) returns exactly HALF the IEEE value for
  every subnormal f16 input (0 < |v| < 2^-14 = 6.10352e-05), while the payload
  writer's own reader, go1b_fp16_to_fp32
  (/data/YoungAi/gguf-tools/quantize/onebit_quant.h:141-159), matches the IEEE
  rule on every pattern tested.  Normals agree exactly in both.

  measured, half bit -> value:
    0x0001   IEEE 5.960464478e-08   vendored 2.980232239e-08   ratio 2
    0x0346   IEEE 4.994869232e-05   vendored 2.497434616e-05   ratio 2
    0x0400   IEEE 6.103515625e-05   vendored 6.103515625e-05   ratio 1  (normal)

The CPU reference path binds its dense cache through `ds4vq_dequant_f32`
(ds4_eg2vq_bind.inc:305-310), so it decodes every subnormal codebook entry at half
magnitude.  The device kernel follows the file (IEEE), so before this is settled
the file, the CPU path and the device path are three different answers — and a
CPU-versus-GPU parity gate would have charged the difference to the kernel.

What it costs on the real artifact (tools/eg2_subnorm.c, out/artifact-subnormal.log):

    payloads                                461
    codebook entries                     7,553,024   (zeros 740,451)
    subnormal entries                        8,893   (0.117741 %)
    |value| range              5.96046e-08 .. 1.48047
    largest subnormal entry            6.09756e-05
    row gains                593,920 entries, 0 subnormal
    decoded weight mass (L1)             1.39618e+13
    error the vendored rule adds           31,851.7   (relative 2.28e-09)

So the defect is real and its effect on this artifact is negligible: 0.12 % of
codebook entries, none larger than 6.1e-05, and a weight-level L1 error of
2.3e-09 relative.  The decision recorded here, and not taken silently: the device
path follows the file's own reader (IEEE), because the file and the writer's
reader are the source of truth; the CPU path's halving is a defect of the
vendored converter, shared with the tree's V4.1 path, and fixing that converter
is a separate change to shared tree code that this unit does not make.

2b. Two defects this slice found in its own kernel, and how they were caught

Recorded because they are the argument for the gate's shape rather than an
embarrassment:

  1. the index-sector stride was the byte count of 256 codewords (384 B) instead
     of 256 columns (96 B), so every slab after the first unpacked the wrong bits;
  2. the unpack used a block-local row index, so every row block above the first
     re-read row 0's index stream.

Both produced plausible-magnitude, entirely wrong results, and both were caught by
the two-reference gate rather than by review: the second survived a first probe
that used ONE index stream for every row (with identical streams, reading the
wrong row is invisible), and was isolated by holding the activations at 1.0 — with
ones-x the codeword decode is the only thing that can move the sum — and by a
Kronecker probe that put a single 1.0 in one activation column.

3. Row P3.2 — bidirectional attention with the symmetric mask
--------------------------------------------------------------

3a. What exists now

  ds4-rs/cuda/eg2vq_attn.cuh        the kernel and its launcher
  ds4-rs/tests/test_eg2vq_attn.cu   its gate
  ds4-rs/Makefile                   tests/test_eg2vq_attn and test-eg2vq-attn

3b. Why new kernel code, and not the tree's existing windowed kernel

The phase doc's row P3.2 states the correction this slice inherits: the tree's
windowed attention kernel does apply a window and does take causal = false, but

  - it is a scalar one-thread-per-(query, head) kernel that refuses `rows > 256`
    and holds a `float score[256]` on the stack (ds4_cuda.cu:42208, :42211), and
  - its window is TRAILING: `first = window && visible > window ? visible - window
    : 0` (:42214), i.e. a query sees the keys before it and none after.

This model needs the symmetric mask: gemma-embedding2.cpp:4 declares
LLAMA_SWA_TYPE_SYMMETRIC and src/llama-hparams.h:524-533 masks at
pos_diff < -n_swa/2 or > n_swa/2, with n_swa = 512 the half-window the file's
1024 doubles to.  A trailing cut silently drops keys the reference attends to for
any item longer than 256 tokens, which is most of this family's documents.

3c. Design

One block per query token, one warp per query head (four warps), so a block's
heads share the same KV rows and read them from L2 once.  Within a warp the key
range [k0, k1] — the window, or the whole item on the four full layers — is split
across the 32 lanes, which is what makes the per-key work a stride-32 walk with
coalesced loads:

  pass 1  each lane's keys' scores into shared, and the warp's maximum
  pass 2  expf(score - max) and the warp's sum (reference: graph:148-165)
  pass 3  output dimensions spread across the lanes; each lane accumulates its own
          dims over all keys, then multiplies by 1/sum

Scale is exactly 1.0f (no 1/sqrt(head_dim)), there is no causal mask, and a zero
denominator yields zero — all three as the reference does them.  Shared is one
float per key per warp, 4 x 2048 x 4 B = 32 KB static; an item longer than 2048
tokens is refused by the launcher rather than truncated, because a plane that
silently covered half an item would be a wrong answer, not a slow one.

3e. What this slice does not prove

1. No tower.  Nothing here is connected to the VQ GEMM of section 1 yet: the two
   kernels are gated separately, and the composition (norms, RoPE, the PLE block,
   pooling) is P3.3.
2. No latency or throughput number.  The gate measures agreement and the mask
   edge; timing attention in isolation would say nothing about the item.
3. Items longer than 2048 tokens are refused, not handled.  The frozen set's
   longest item is 1414 tokens, so nothing in this project's tests reaches the
   limit — which is exactly why it is refused rather than assumed.
4. Nothing about the geo-mean of keys, the KV cache state, batching across items
   or any serving shape: this is the embeddings path, where every item attends to
   itself and nothing is cached.
5. No other attention variant (no softcap, no sliding-type variants, no
   different scale) was tested, because this model has exactly one.

4. Row P3.3, step 1 — the tower's small device ops
---------------------------------------------------

4a. What exists now

  ds4-rs/cuda/eg2vq_ops.cuh        the primitives the two kernels do not cover
  ds4-rs/tests/test_eg2vq_ops.cu   their gate

4b. The ops, and the two stated deviations

Each mirrors one expression of the CPU reference forward (ds4_eg2vq_graph.inc,
citations in the kernel header):

  embed       one q8_0 table row, scaled by sqrt(n_embd)      graph:196-208
  rms         row RMS with an optional weight, eps inside the
              square root, the sum in double                    graph:47-53
  rms_head    the same per head vector, weighted on q and k
              and weightless on v                               graph:264-277
  rope        NeoX over the whole head, pairs (i, i + hd/2)     graph:60-77
  gelu_mul    gelu(gate) * up at ggml's tanh coefficients       graph:39-41, :307-309
  proj768     per token: RMS by output_norm, then a dot with
              each of the 768 bf16 rows, accumulated over the
              item; then the mean pool and L2                    graph:339-367

Two deviations from a literal transcription of the graph's *code* (not its
arithmetic), both because of this build's own flags rather than a preference:

  - The RoPE angles come from a table the caller builds.  --use_fast_math compiles
    sinf/cosf to the SFU approximations, whose fp32 argument reduction loses about
    8e-05 rad at the largest angle this tower produces; a table built with the
    graph's own angle accumulation (theta starts at the position and multiplies by
    theta_scale in f32, one step per pair) and double-precision sine and cosine
    reproduces the reference's angles exactly and computes only the trig more
    accurately.  Measured: bit-identical output (rel RMS 0.000e+00).
  - Norm weights arrive as f32, the form the CPU path reads them into (graph:57-59);
    a few hundred floats per layer.

The RMS rows sit at f32 rounding (~6e-08): the kernel and the reference accumulate
in double and differ only in the reduction order.  RoPE and the embedding gather are
bit-identical.  The one number that is not at rounding is the GELU: 2.39e-06
relative, with a 1.967e-05 largest absolute difference, and its bound is 1e-05 for
that measured reason — tanhf is a library function that --use_fast_math compiles
differently from the libm one the CPU reference links.  It is stated rather than
hidden because a later unit that needs a tighter tower bound will find this term
first.

4d. What this step does not prove

1. No tower.  These ops are not composed with the GEMM and the attention kernel
   yet, so there is still no item on the device, no tokens/s and no VRAM number.
2. Nothing about the adapter: the RoPE tables are per-layer data the adapter must
   build (2 x n_pos x head_dim/2 floats — about 1.4 MB at 1,414 tokens on the full
   layers) and the payloads are still not device-resident.
3. The 768 projection uses one block per token with an atomic accumulation: right
   for 768 outputs, unmeasured for anything wider.
4. The GELU bound is the fast-math tanh's, not the arithmetic's; the tower gate may
   need a precise tanh and that is a change, not an assumption.

5b. The contract, and why it is a header

The adapter never reaches into the CPU binder's structs; the two sides agree
through ds4_eg2vq.h, and the agreement is data, not convention:

  records  217 in DS4_EG2VQ_REC_* order — PLE_PROJ (0), then nine per layer from
           1 + il*9 (Q, K, V, O, FFN_GATE, FFN_UP, FFN_DOWN, PLE_GATE, PLE_PROJ).
           eg2vq_device_tables() builds them from tensor->abs_offset and dim[0]
           for the same tensors the CPU binder walks, so the device plan and the
           CPU plan are the same 217 tensors or neither.
  aux      196 slots = 4 + 24*8: four globals (OUTPUT_NORM, PLE_NORM, OUTPUT,
           TOKEN_EMBD) then eight per layer (INPUT_NORM, ATTN_POST, FFN_NORM,
           FFN_POST, PLE_POST, Q_NORM, K_NORM, SCALAR).
  KV width a static assertion that the sliding layers' KV width (2 heads x 256)
           equals the full layers' (1 x 512) = 512.  That equality is what lets
           ONE KV plane serve both layer kinds (5c), so the assertion is why the
           buffer is legal rather than lucky.

Three type rules, each decided by what the CPU path reads:

  q8_0      the token table stays q8_0 on the device and is dequantized in the
            gather kernel: a row is read per token id, and the table is
            136.02 MiB (262,144 x 512), so expanding it would cost more than the
            entire text tower.
  bf16      the 768 projection stays bf16 and is read in-kernel, as the graph
            reads it.
  f32       everything else is widened ON THE HOST from its file type, because the
            CPU path reads the norm vectors as f32 (graph:57-59) and a narrow
            in-kernel read would add rounding the reference does not have, for a
            few hundred floats per layer.  The widening is the IEEE reading for
            both: bf16 as u << 16, f16 through eg2vq_ops_half_to_f32.

5c. Design: one payload arena, one workspace, one table pair

Binding checks before it copies, and each check refuses rather than clamps:

  - every record's file span, so a truncated or misplaced tensor is caught at
    bind rather than decoded into plausible garbage;
  - the payload's own header against the record it came from (magic "DQVQ",
    dim 4, nc 4096, rows, cols), so a payload cannot run at the wrong geometry;
  - rows % 64 and cols % 256, the GEMM's tile, so no partial tile reaches the
    kernel;
  - the q8_0 table's byte length against rows*(cols/32)*34, and the bf16
    projection's shape against [768][512].

Then one device arena holds all 217 payloads and a second holds the aux slots,
and the process keeps both for its lifetime.  This is where "weights
device-resident" stops being an intention: measured, payload 55.94 MiB, weights
137.04 MiB.

The workspace is the 17 planes eg2vq_gpu_layout_of computes — ids, out, h, x, f,
a, q_swa, q_full, kv, attn_swa, attn_full, fg, fu, fd, pg, pp, ple — each 16-byte
aligned and scaled by max_tokens.  The KV plane is max_tokens * 512 * 4 B on both
layer kinds, on the strength of the 5b assertion.  At max_tokens 2048 it is
212.01 MiB, the largest single item of the run's 414.0 MiB.

The RoPE table pair ([swa cos][swa sin][full cos][full sin]) is built once per
context, on the host, with the graph's own f32 angle accumulation and
double-precision trig — the section-4 deviation applied per layer.  The 24 layer
scalars are read back to the host and passed as kernel arguments.

Refusals, all before any work is done: max_tokens > 2048 at create
(EG2VQ_ATTN_KEYS_MAX), and an out-of-range id, n_ids == 0 and n_ids > max_tokens
at embed.

5d. Design: the sequence IS the CPU graph's op order

ds4_gpu_eg2vq_embed runs one item through 24 layers and the head in
ds4_eg2vq_graph.inc:169-370's exact order:

  embed     q8_0 gather of the ids, scaled by sqrt(n_embd)              :196-208
  PLE       PLE_PROJ gemm, scale 1/sqrt(512), row RMS over n_tok*24     :211-232
  per layer
            a. rms(x, ln_in)                                            :240-243
            b. k, q, v gemms                                            :246-256
            c. per-head RMS on q and k (weighted) and on v (weightless),
               then RoPE on q and k                                     :264-292
            d. attention: the symmetric window on the five sliding layers,
               the full mask on 5/11/17/23                              :295-306
            e. o gemm                                                   :308
            f. rms(a, ln_ap) + add — the post-attention residual        :313-318
            g. rms(f, ln_fn), gate and up gemms, gelu-mul, down gemm    :321-333
            h. rms(fd, ln_fp) + add — the post-FFN residual             :336
            i. ple_gate gemm, gelu_mul_strided against the PLE block,
               ple_proj gemm, rms(pp, ln_pp) + add                      :340-360
            j. scale by layer_scalar[il]                                :362

Every call in that list is a gated primitive: section 4's ops, section 1's GEMM,
section 3's attention.  The tower contains no new arithmetic at all — the
adapter's contribution is the order, the buffers and the binding.

payload once per 64-token tile, so the 1414-token item reads the tower's
58,658,409 B about 23 times, about 1.35 GB, in 564.94 ms — an achieved payload rate
of 2.4 GB/s.  That is arithmetic on the payload size and the item's wall time, not
a traffic counter, so it is evidence that the item is NOT bandwidth-bound, not a
measurement of traffic: no Nsight or counter was read, and no other geometry was
tried.

6. What the device path does not prove
--------------------------------------

1. No entry point, and no tower in the runtime.  The tower's only callers in the
   tree are the two parity harnesses: a repo-wide grep for ds4_eg2vq_ref_embed and
   ds4_gpu_eg2vq_embed finds the declarations (ds4_eg2vq.h:132, :247), the
   definitions (ds4_eg2vq_graph.inc:169, ds4_eg2vq_gpu.cuh:395) and nothing
   outside tests/.  The device adapter is not registered in ds4.c's family path
   either: the family BINDS (ds4.c:10287-10290, eg2vq_bind) but no runtime
   function calls the device tower.  So every number above is reachable only by
   building and running the gate.

2. The decode path does not refuse; it dies.  Measured, twice, on the artifact:

       ./ds4 -m out/EmbeddingGemma-2-914f7f8-vq4x4096-q80token-gemma_vq.gguf -p hello -n 1

   initializes CUDA on the 4070 SUPER, prints the catalog (1376 tensors, 0
   routed-expert, 1 artifact-additive), the residency ledger and the 0.41 GiB
   device mapping, and then dies with SIGSEGV (exit 139, core dumped).  The second
   run reproduced it, and --cpu does the same, so it is not a GPU fault.  The
   cause is a missing guard for family 16 in the generation path: the variant has
   a shape case (ds4.c:2881) and a bind arm (:10287) but no forward or session arm,
   so the generic prefill reaches embed_token_f16, which dereferences
   w->token_embd — a slot gemma_vq never populates, because its token table is
   bound under w->eg2vq (ds4_eg2vq_bind.inc:233-239).  Recorded here because the
   obvious command a reader will type produces a core dump instead of an error;
   the fix (a refusal, plus the embed verb and route that make the checkpoint
   usable) is phase 6.
3. The gate's own speedup is against its -O0 build, so its 23.0 tokens/s is a
   debug-shaped CPU number.  The fair comparison is in 5e and 5f: 9.9x on short
   queries, 18.1x on retrieval-length documents.  What does NOT depend on the CPU
   build is the parity column: the device leg computes the CPU leg's arithmetic,
   and the CPU leg reproduces the committed oracle raw exactly.
4. One item at a time, on the default stream, in one process.  No batching and no
   concurrency is measured; ds4_current_stream() returns 0 (the legacy default
   stream) unless a capture or side stream is active, which is why the per-item
   blocking copies are correctly ordered.
5. The workspace is sized by max_tokens, not by the item: at 2048 it is
   212.01 MiB, 51% of the run's 414.0 MiB, while the longest item in this
   project's tests is 1414 tokens.  A smaller max_tokens would cut it roughly
   linearly (the KV plane dominates) and nothing tried that.
6. No quality statement.  The device leg consumes the same payloads the CPU leg
   does, so it cannot move the codec's cost; that stays phase 5's subject (row
   X.7, still OPEN).
7. Run B is a twelve-item sample, not the frozen set.  The full 583 items at -O0
   is roughly two hours of CPU, which is why the sample exists; at the -O3 rates
   above it is about 11.8 minutes of arithmetic (107,029 tokens at 150.6
   tokens/s), which is an inference, not a measurement.
8. No portability claim: sm_89, this card, as row X.9 keeps it.  And no variant of
   the kernels was tried — the token tile, the key plane and the payload re-read
   are all first-cut choices — so the device numbers are a floor, not a best case.

7. Risk analysis (global rule 20, for the device path as a whole)
-----------------------------------------------------------------

Decision: move the gemma_vq text tower's compute onto this card's GPU, with the
VQ payloads consumed in-kernel and the weights device-resident, and gate it on
parity, latency and VRAM (P3.3).

External risks, each with the evidence that was checked:
- The card is not the deployment target.  install.sh:112-116 still refuses
  non-GB10 machines by design, so nothing here says the kernel runs on the Spark
  (sm_121a): its instructions are sm_80-era and resolve there, but that is
  reasoning, not a measurement, and the row X.9 evidence for the Spark is the
  tree's own sm_121a object set (out/cuda-sm89-objectset.log).  UNVERIFIED on
  another device.
- Driver/toolkit drift.  The build is pinned by the recorded arch
  (.ds4-cuda-config.mk: CUDA_ARCH := sm_89) and nvcc 13.3.73; a toolkit change
  can move f32 contraction and with it the parity numbers in 1d.  The gate
  re-measures rather than trusting this file (section 1c).

Decision risks, each with its evidence:
- The payload is re-read once per 64-token tile (measured above as the GB/s
  column): a long item reads each matrix ceil(tokens/64) times.  For a 1414-token
  document that is 23 passes over the text tower's 55.9 MiB of payload
  (58,658,409 B over 217 payloads, summed from out/artifact-manifest.tsv), about
  1.3 GB.  Measured at tower scale now (unit 18): the 1414-token document took
  564.94 ms on the device (section 5f), an achieved payload rate of 2.4 GB/s, so
  the re-read is not what bounds the item and the mitigation (a larger token tile)
  is a one-constant change nothing has needed yet.  CORRECTION (unit 18): this line said "23 passes over
  437 MB" until the device plan measured it; 437,508,416 B is the whole artifact
  FILE (docs/artifact-gguf-gate1b.txt), not the payloads, and the tower uses 217 of
  the 461 payloads (the artifact also VQs the audio and vision towers).  All of
  them together are 237,289,117 B / 226.3 MiB.
- In-kernel decode costs instructions that a pre-decoded dense matrix would not.
  The plan of record forbids expanding the payloads to dense on the device, and
  this slice keeps that rule; the alternative was not measured, so no claim is
  made that in-kernel decode is faster than pre-decoding to f16 — only that it is
  the committed design and it is now measurable.
- Occupancy.  40 KB of static shared per block caps blocks per SM; the measured
  throughput is what it is (3.1 TFLOP/s, ~9 % of FP32 peak), and no variant was
  tried.  Treat 3.1 TFLOP/s as a floor, not a ceiling.
- The CPU reference path's subnormal defect (section 2) will make CPU and GPU
  differ slightly at the tower gate even when both are correct.  Measured size:
  2.3e-09 of the weight L1 mass, i.e. far below any parity bound in use.

- The device path is unreachable from the runtime, and the unguarded decode path
  is a crash rather than an error (section 6, items 1 and 2 — both measured).  A
  reader who tries the shipped binary on this artifact gets a core dump, and none
  of the device work is reachable without the entry point.  Prevention, in this
  order: the refusal guard first, so the failure is a message instead of a
  segfault; then the embed verb and the route, which is phase 6.

Prevention in place: the kernel refuses a payload whose header disagrees with the
caller's geometry (measured: the wrong-geometry case leaves the output untouched),
so a mis-bound tensor cannot decode silently; the gate re-derives both references
from the payload bytes on every run; and the arch is recorded so a rebuild here is
card-native without a flag.

Rollback: this slice is additive.  `git revert` of the ds4-rs commit, or simply
not building tests/test_eg2vq_vq — no existing object, header or binary changed,
and the CPU path is untouched.

Residual risk, and how this unit resolved it: the premise of this phase ("it
should be much faster") is now measured rather than argued — 9.9x per item on the
frozen set's short queries and 18.1x on retrieval-length documents, against the
same CPU source compiled with the tree's own flags (sections 5e, 5f).  The phase is
not re-scoped, and the earlier version of this paragraph ("if P3.3 does not beat
the CPU path by a wide margin, re-scope rather than tune") is answered: it does.
What remains residual is not speed but REACH — with no entry point and no guard,
the only way to obtain a vector today is to build and run the gate, and the obvious
CLI command segfaults (section 6, items 1-2).  That is a defect of the integration,
not of the device path, and it is phase 6's first job.
