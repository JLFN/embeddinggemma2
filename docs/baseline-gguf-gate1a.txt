Findings that changed the plan (each measured, not assumed)

1. One-dimensional tensors and *_norm.weight must be F32, not BF16
   (conversion/base.py:1244-1246: "Most of the codebase that takes in 1D tensors or
   norms only handles F32 tensors", applied before the ftype default at :1305-1315).
   Measured the other way first: an all-BF16 build of the file loads and then dies
   in the graph with
     binary_op: unsupported types: dst: f32, src0: f32, src1: bf16
   repeated once per worker thread, before any embedding is produced. With the 194
   one-dimensional tensors written F32 the same file runs to a finished vector. That
   is 194 tensors, not a handful: 24 x {attn_norm, attn_q_norm, attn_k_norm,
   post_attention_norm, ffn_norm, post_ffw_norm, post_norm, layer_output_scale} plus
   output_norm and per_layer_proj_norm.

2. attention.sliding_window is written DOUBLED: 2 x 512 = 1024
   (conversion/gemma.py:824-825, "HF sliding_window is bidirectional, llama.cpp
   expects the full window size"), and the loader's symmetric mask is
   |p1 - p0| > n_swa/2 (src/llama-hparams.h:524-533). The half-window a token sees
   is therefore 512, i.e. a 1025-wide span, not the 256/513 that reading the
   checkpoint's sliding_window straight into n_swa would give. Phase 4 and phase 7
   must use the doubled value; the phase-0 contract's key table said 512 and is
   corrected in the same commit.

3. attention.sliding_window_pattern is written as a BOOL ARRAY of per-layer flags
   derived from the checkpoint's own layer_types (conversion/gemma.py:681-682), not
   as the scalar 6; the loader prefers the array when present
   (src/llama-model.cpp:3902-3912). Both encode the same pattern for this model —
   is_swa = il % 6 < 5 (src/llama-hparams.cpp:8-17) — and the writer cross-checks
   the array against that formula and refuses to write if they disagree.

4. The converter's key set for this arch also includes attention.causal = false,
   rope.dimension_count (= 512) and rope.dimension_count_swa (= 256), and
   gemma-embedding2.pooling_type = 1 (MEAN, from 1_Pooling/config.json via
   _try_set_pooling_type). No tokenizer.ggml.pre: the loader pins "gemma4" itself.

5. Norm weights ship VERBATIM. Gemma3Model adds +1.0 to every norm.weight
   (conversion/gemma.py:131), Gemma4Model overrides norm_shift to 0.0
   (conversion/gemma.py:637-639) and EmbeddingGemma2Model inherits that — so no
   shift here, and the port must not apply one either.

6. The tokenizer is gemma4 BPE and REQUIRES merges (src/llama-vocab.cpp:2236-2276:
   "cannot find tokenizer merges in model file" is a hard throw). The checkpoint's
   514,906 merges are in the list-of-pairs form, which the converter escapes as
   U+0101 for any part containing a space (gguf-py/gguf/vocab.py:202-220); no part
   of this vocabulary contains a space, so the escape never fires here. The token
   list is the 262,144 model.vocab keys by id, the scores are -1000.0 throughout
   (gguf-py/gguf/vocab.py:659-662), and the types are BYTE for <0xNN>, CONTROL for a
   special id, NORMAL otherwise (gguf-py/gguf/vocab.py:651-657).
