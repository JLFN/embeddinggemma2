What the row asked for (docs/ds4-gemma-port-phases.md:192): "Serving capability
and native-limit arms for the new family" -- a per-family serving-cap entry,
because "a decode-shaped cap does not describe an embedding model" -- and

1. The two caps, and where each number comes from
-------------------------------------------------

    item_tokens_max  2048   the device attention kernel's key plane:
                            cuda/eg2vq_attn.cuh:49 (EG2VQ_ATTN_KEYS_MAX), which
                            ds4_eg2vq.h:140 (DS4_EG2VQ_MAX_TOKENS) mirrors and
                            ds4_eg2vq_gpu.cuh:45-46 static-asserts equal.
    batch_rows_max   8192   the row budget of one batched call. A POLICY of this
                            port: nothing in the artifact states a batch width.
                            At the layout's own charge of 108,548 B per row
                            (106.0 KiB; ds4_eg2vq_gpu.cuh:72-99 sums to 27,136
                            f32 planes plus the 4-byte id) that is 848.0 MiB of
                            device workspace, four times the measured 212.01 MiB
                            at 2048 rows (docs/eg2vq-device-gate7.txt:407-411).

Neither number is the family's `ctx_max` (262144, the file's own
`gemma_vq.context_length` = the checkpoint's max_position_embeddings). That field
answers "which session could be created", which for an encoder is not a question a
caller asks; the caps answer "what may I send", which is. Both live in
crates/ds4-core/src/gemma_vq.rs and are reached through
`ds4_core::embed_caps(family) -> Option<EmbedCaps>`, `Some` exactly for
ModelFamily::GemmaVq -- the same family-keyed shape the tree already uses for
serving_host::family_native_limit, rather than a field on ServingCaps whose
vocabulary (banks, reuse, speculation, context) is decode-shaped and empty here.

2. One number, three files -- now held together by a test
---------------------------------------------------------

The item ceiling existed in Rust, in a C macro and in a CUDA enum, with the last
two asserted equal at compile time and nothing asserting the first. The new
crates/ds4-core/tests/eg2vq_serving_caps.rs READS both C sources (include_str!:
this crate builds without the C tree) and fails if either disagrees with the Rust
constant, so a divergence is a red test rather than a mismatch discovered by a
refused request. It also pins the per-row workspace arithmetic the batch budget's
comment quotes, and that a decode family reports no embedding caps at all.

3. Enforcement, and what a live run shows
-----------------------------------------

Enforced in three places, each the one that can see the number first:

  * crates/ds4-core/src/lib.rs, `Model::embed_gemma_vq`: an item past the ceiling
    is refused before the FFI call, so the message is the same on every backend
    (the C refusal in ds4_engine_embed_gemma_vq stays as the second line, keyed
    to the same macro).
  * crates/ds4-server/src/serve.rs, `run_embed`: both caps, after tokenization and
    before the tower, as a 400 in the OpenAI envelope naming the cap -- a request
    that exceeds a limit the server itself advertises on /health is a client
    error, not an engine fault. `embed_fail` keeps the 500 for a real fault.
  * crates/ds4-core/src/serving_host.rs: the family's native limit and chunk
    default are the tower's ceiling (2048), not the generic 16384, and
    DS4_GEMMAVQ_PREFILL_CHUNK cannot lift them past it: an encoder has no prefill
    chunk to size, and advertising one the tower cannot hold would be a lie in
    the plan.

this unit. Run over the CUDA backend on the VQ artifact

5. What this unit does NOT prove
--------------------------------

  1. No batching. An array input still embeds its items one at a time over the
     single bound plan; batch_rows_max bounds the work a request may ask for, and
     after the next slice it bounds the memory of one packed call, which is the
     same number for the same tokens.
  2. No device-path throughput claim. Nothing here measures items/s, and the
     route's per-item serialization is exactly what the batching slice exists to
     change.
  3. The caps are two policy numbers around one measured fact. item_tokens_max is
     a kernel property; batch_rows_max is this port's choice, and a different
     choice would be a different document, not a different measurement.
  4. No claim about the 512/256/128 output widths or the task names: those stay
     owned by ds4_core::mrl_truncate and ds4_core::st_prompt, and are deliberately
     not duplicated into the caps.
  5. The refusal checks are one live run on this card over the CUDA backend; the
     CPU backend reaches the same Rust refusal before the FFI call (and the C one
     behind it) but was not driven over HTTP in this unit.
